---
title: Turn on billing
description: Wire Polar checkout, portal, webhooks, entitlements, and usage when credentials and catalog are bound.
---

Billing is `configured` in `product.config.ts`. `BillingService` always exists. Checkout, portal, webhooks, and usage stay quiet until Polar credentials are set. Empty `POLAR_ACCESS_TOKEN` keeps fake billing. Do not register the Better Auth Polar plugin. An empty token would break sign-up.

## Steps

1. Create a Polar organization and access token (sandbox or production).
2. Create products in Polar and copy their product IDs. To grant a capability, give the benefit a `feature` metadata key (for example `feature: ai.chat.fast`).
3. Add a webhook in Polar that POSTs to your API Worker at `/api/webhooks/polar`. Copy the signing secret.
4. Set in the API Worker env (`.dev.vars` for plain wrangler, root `.env` for `alchemy:dev`, a stage file on deploy):

```bash
POLAR_ACCESS_TOKEN=pol_your_token_here
POLAR_SERVER=sandbox  # or "production"
POLAR_WEBHOOK_SECRET=whsec_…
# Optional. Unset → Polar's default success page.
# POLAR_CHECKOUT_SUCCESS_URL=https://app.example.com/billing/success

# Product catalog: POLAR_PRODUCT_<SLUG>=<product_id>
POLAR_PRODUCT_PRO=prod_abc123xyz
POLAR_PRODUCT_ENTERPRISE=prod_def456uvw
```

Under Alchemy, only keys listed in `infra/api.ts` `env` reach the Worker. `POLAR_PRODUCT_PRO` and `POLAR_PRODUCT_ENTERPRISE` ship there. Add a `Config.String("POLAR_PRODUCT_<SLUG>").pipe(Config.withDefault(""))` entry for each new slug. Plain wrangler reads any key from `.dev.vars`.

Polar must reach `/api/webhooks/polar` on a public URL. Local `alchemy:dev` needs a tunnel or Polar's sandbox delivery against a deployed Worker.

5. Restart `alchemy:dev` or redeploy so the Worker sees the env.
6. Call billing oRPC from a signed-in Team session. The organization id comes from the session, not the client.

   - `billing.createCheckout({ productSlug })` → checkout URL (Team `owner` or `admin`)
   - `billing.customerPortal({})` → portal URL (Team `owner` or `admin`)
   - `billing.snapshot()` → projected capabilities and limits (any member)

## What you should see

With credentials and catalog bound:

- `createCheckout` returns `{ kind: "url", url: "https://buy.polar.sh/..." }`
- `customerPortal` returns `{ kind: "url", url: "https://polar.sh/.../portal/..." }`
- Polar `external_customer_id` is the Better Auth organization id
- Verified webhooks return `202` and write `billing_webhook_event` plus `billing_entitlement`
- Webhooks dedupe on the Standard Webhooks `webhook-id` header. Polar retries keep their id. Distinct events for one subscription each get processed
- Bad signatures, missing `webhook-*` headers, or a timestamp more than 5 minutes off return `403`. Missing `POLAR_WEBHOOK_SECRET` returns `503`
- Only benefits with `feature` metadata grant a capability. The Polar benefit type alone grants nothing
- `canUse` / `limit` / `remaining` read the Postgres projection first, then Polar customer state
- Usage goes through `billing_usage_outbox`, an in-process flush, the `billing.usage` queue job, then Polar `events.ingest` with `external_id` equal to the operation id
- `ai.complete` requires an active Team and `canUse("ai.<capability>")` when Polar is configured. Usage failures after a successful completion are logged and the model reply still returns

Without credentials:

- Checkout and portal return `{ kind: "unconfigured" }` (still owner/admin only)
- Entitlements stay denied
- Fake AI runs unmetered, with or without a Team

## Access rules

| Caller                  | `createCheckout` / `customerPortal`                           | `snapshot`     |
| ----------------------- | ------------------------------------------------------------- | -------------- |
| Signed out              | `UNAUTHORIZED`                                                | `UNAUTHORIZED` |
| No active Team          | `BAD_REQUEST` "Select a Team to continue."                    | `BAD_REQUEST`  |
| Team `member`           | `FORBIDDEN` "Only Team owners and admins can manage billing." | Allowed        |
| Team `owner` or `admin` | Allowed                                                       | Allowed        |

The session only carries an organization id when a `member` row backs it. A user removed from a Team loses billing access on the next request.

## Product catalog

The server maps product slugs to Polar product IDs. Clients request a slug such as `"pro"`. The server checks the catalog before calling Polar, so Polar IDs stay out of client code. An unknown slug returns `BAD_REQUEST` "Unknown product."

Slugs are normalized to lowercase:

- `POLAR_PRODUCT_PRO=prod_abc123` → slug `"pro"`
- `POLAR_PRODUCT_STARTER=prod_def456` → slug `"starter"` (add it to `infra/api.ts` under Alchemy)

## Customer identity

The billable customer is the Better Auth organization. Polar stores it as `external_customer_id`. oRPC handlers refuse checkout, portal, and snapshot unless the session has a Team.
